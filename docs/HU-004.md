# HU-004 - Consulta del Detalle de una Película

## Objetivo

Implementar la consulta del detalle de una película, sus funciones futuras y películas recomendadas utilizando la arquitectura existente del proyecto.

## Endpoints implementados

### GET /movies/:id

- propósito: Obtener el detalle completo de una película.
- parámetros: `id` en path.
- query params: ninguno.
- respuesta esperada: objeto `Movie` con relaciones `actors`, `genres`, `banners` y `releases`.
- códigos HTTP:
    - `200 OK` cuando la película existe.
    - `400 Bad Request` cuando el id es inválido.
    - `404 Not Found` cuando la película no existe.
    - `500 Internal Server Error` para errores inesperados.

### GET /movies/:id/functions

- propósito: Obtener las funciones futuras de una película.
- parámetros: `id` en path.
- query params: `cityId` opcional para filtrar funciones por ciudad.
- respuesta esperada: arreglo de funciones futuras con datos de `functionType`, `room`, `roomType`, `cinema`, `city`, `ticketsCount`, `seatLocksCount` e `isSoldOut`.
- códigos HTTP:
    - `200 OK` cuando la consulta es exitosa.
    - `400 Bad Request` cuando el id de película o ciudad es inválido.
    - `500 Internal Server Error` para errores inesperados.

### GET /movies/:id/recommendations

- propósito: Obtener recomendaciones de películas similares.
- parámetros: `id` en path.
- query params: ninguno.
- respuesta esperada: arreglo de películas similares a la película solicitada.
- códigos HTTP:
    - `200 OK` cuando la consulta es exitosa.
    - `400 Bad Request` cuando el id es inválido.
    - `500 Internal Server Error` para errores inesperados.

## Arquitectura

Controller → Service → Repository → Sequelize

- El Controller recibe la petición, valida parámetros y delega la lógica de negocio al Service.
- El Service aplica reglas de negocio y llama al Repository.
- El Repository interactúa con Sequelize para obtener los datos.

## Relaciones utilizadas

- `Movie` con `actors` a través de `MovieActor`.
- `Movie` con `genres` a través de `MovieGenre`.
- `Movie` con `banners` a través de `MovieBanner`.
- `Movie` con `releases` mediante `MovieRelease`.
- `MovieRelease` con `functions` mediante `Function`.
- `Function` con `functionType`.
- `Function` con `room`.
- `Room` con `roomType`.
- `Room` con `cinema`.
- `Cinema` con `city`.

## Reglas de negocio

- RN-014: Solo se retornan funciones futuras basadas en `startsAt` y `active`.
- RN-015: Las funciones agotadas se devuelven con `isSoldOut`, calculado a partir de `ticketsCount >= room.capacity`.
- RN-016: El backend devuelve `trailerUrl` directamente desde el modelo `Movie` para que el frontend embeba el video de YouTube.

## Decisiones técnicas

- Se creó un `IMovieService` con tipo `MovieFunctionDetail` para evitar el uso de `any` en la respuesta de funciones.
- La lógica de disponibilidad se basa en el conteo de tickets y la capacidad de sala. Este cálculo se hace en el servicio, manteniendo al repositorio enfocado en la consulta de datos.
- Las recomendaciones se generan sobre géneros compartidos y excluyen la película actual.

## Limitaciones o pendientes

- La implementación de RN-015 usa el conteo de tickets y la capacidad de sala para determinar si una función está agotada. El MER actual no define un campo explícito de disponibilidad por función.
- Si la base de datos no tiene funciones relacionadas o no hay tickets, se considera que la función no está agotada.
